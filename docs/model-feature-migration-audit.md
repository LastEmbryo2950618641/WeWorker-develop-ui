## 内置模型在哪一步消失

1. `808619e7` 在旧历史加入 `builtin`；`3e6c9d9` 加入 `builtin_dev`。
2. 本地 reflog 显示，2026-09-28 16:10 从 `origin/develop` 的 `0060bde` 重新建立当前 `develop`，该公开基线没有上述内置供应商。
3. 随后依次迁入 `2d1909e`、`c071b2f`、`fbe33d4`，分别对应旧分支的 `3e6c9d9`、`29499e2`、`67f0055`。这是选择性迁移，不是完整合并旧分支。
4. `2d1909e` 的 ROADMAP 明确记载：“不导入旧版内置凭据和内部 Provider”。提交说明仍有“built-in providers”字样，但实际迁移结果没有包含这部分，不能只根据提交说明判断功能存在。
5. 当前 `build-profile.json`、Backend 注册表和 Renderer 默认列表均不注册内置模型；`builtin-provider.ts` 也不存在。Renderer 中残留的内置卡片分支因此不可达。

所以，内置模型不是最近一次导航改动删除，也不是远端新增 11 个提交删除；它在重建公开分支及后续选择性迁移中未被带入。旧分支中仍保留这项实现。

旧实现包含硬编码服务凭据和内部 Provider 配置。恢复时应使用现有 Profile/Overlay 边界及独立凭据供应方式，不能把旧文件原样搬入公开源码，也不能仅显示一张不可使用的卡片就称为恢复完成。

独立探索配置的问题不等于“自定义供应商的高级 OpenAI 地址”可以完整替代：后端仍优先采用已保存的独立探索配置，而该配置的 Key 和模型可以与主模型不同。入口消失会使已有独立配置无法通过界面修正。

## 仍保留及尚未同步的内容

- API 探索、网站探索agent、扩展连接组件和后台能力仍在。现有未提交 Renderer 改动已将探索入口和扩展状态放到独立侧栏入口，本次保留这些改动。
- 微信、企微、QQ 通道代码仍在；飞书由本地迁移增加。已检查的企微代码删除部分属于上述状态后缀处理，不能据此说企微通道被删除。
- 对 `server.ts` 中直接声明的 HTTP 路由做静态集合比较：远端已有路由无缺失，本地增加 `/settings/provider/add`。此检查不证明每个路由内部行为相同，也不等同端到端验收。
- 本地尚未合入远端的 11 个提交主要是公开网站 Adapter 迁移与扩展捕获改进，包括携程、新站点和命令覆盖。这些是“尚未同步”，不是本地删除远端功能。
- `active_provider` 响应字段在实例模式下返回配置 ID，现有列表、保存、探测和激活代码按该 ID 配合使用；名称有歧义，但不能单凭返回实例 ID 认定切换故障。未做协议重构。

## 验证与限制

- Backend 7 个测试文件、98 项通过：模型实例、供应商可见性、供应商注册与探测、探索模型配置、模型接入、飞书通道、会话压缩。
- Renderer 6 个测试文件、53 项通过：模型选择与设置、会话压缩、探索生成与恢复、网站探索导航和事件。
- Backend 测试输出有 Windows 不支持 `which claude` 的诊断，测试退出码仍为 0；不据此声称桌面启动或真实模型调用通过。
- 上述测试没有验证设置页实际挂载独立探索配置，也不能发现所有可见入口回退。测试通过不否定本报告确认的遗漏。
- 未恢复内置模型，未运行真实模型/渠道联调，未修改凭据、Profile、发布流程或数据库；本报告不是全功能无回归证明。

建议恢复顺序：先补回独立探索配置入口与模型接入行为，再基于独立部署配置恢复内置服务，最后单独同步并验证远端 Adapter 提交。保留当前 WeWorker 配色和左右布局，无需整体回退界面或合并旧内部历史。
